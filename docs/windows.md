# Windows x64 alpha

The source tree builds a **Windows x64 (`x86_64-pc-windows-msvc`)** desktop app and an **unsigned per-user NSIS installer** next to the existing macOS ARM64 app. It is an **experimental build outside the supported macOS ARM64 platform**; published installers and their checksums are listed in the [release records](history/releases.md). Its accepted qualification is hosted **Windows Server 2025 x64 only**, **not** Windows 11 support: no Windows 11 machine has run this installer/app. Windows ARM testing is deferred; availability of an ARM runner is not evidence. Windows 10 and Windows ARM64 are not targets.

## What is the same

The app is the same private, single-user Tauri host with its owned loopback Next.js/Node/SQLite backend, native Settings/onboarding, separately managed integrations and explicit existing-data upgrade procedure ([desktop runtime](desktop.md)). Settings, provider keys and tokens remain owner-private plaintext files protected by OS access control (same-user and administrator processes and backups can read them; there is no encryption). Schemas, defaults and data formats do not change by platform, and no data moves between machines automatically.

## Windows mechanisms

| Concern                                        | Windows implementation                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Private settings, database publication, tokens | Handle-relative opens that never traverse junctions/symlinks/reparse points; new private files/directories get a protected DACL for the current user and SYSTEM only (inherited by files later created inside); existing objects must be user-owned with no ordinary foreign access and are never repaired; file-ID identity; exclusive creation; renames of the held handle relative to the pinned parent (no-replace unless replacement is already authorized); identity-checked deletes; a per-directory current-user lock released on process exit. |
| Paths                                          | Local drive-letter canonical paths only (`C:\…`). UNC/network shares, `\\?\`/device paths, relative-drive, `/` spellings, alternate data streams, reserved device names, trailing dots/spaces and case/8.3/junction/subst aliases are refused.                                                                                                                                                                                                                                                                                                          |
| Owned processes                                | Bundled `node.exe`, helpers and tools start suspended inside a kill-on-close Job Object; their descendants cannot escape it. Quit closes the backend's liveness pipe (graceful drain), then the job ends the whole tree. If the host dies, the backend settles its database lease and exits, which ends the rest of the tree. Nothing is stopped by name, port or parent PID.                                                                                                                                                                           |
| Database writers                               | The canonical writer lease is shared across case/alias spellings, and a database open in another process is refused (an exclusive no-sharing probe replaces macOS `lsof`).                                                                                                                                                                                                                                                                                                                                                                              |
| Tools                                          | The app launches no external tool for Garmin (no Python, uv or uvx); bundled Node reads the official Personal API in-process. Child PATH is the system directory only.                                                                                                                                                                                                                                                                                                                                                                                  |
| ChatGPT sign-in                                | The helper sends the official authorization URL to the native host over its private pipe; the host re-validates the exact route and opens it with `ShellExecuteExW`. No app-created shell, argument list, environment or file carries the URL, but Windows then hands it to the user's default browser on that browser's own command line (OS behaviour). The usage page uses the same fixed opener.                                                                                                                                                    |
| Legacy Keychain adoption                       | macOS-only. On Windows it refuses and explains private re-entry; originals are untouched.                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Menus and editing                              | A **File** menu with **Settings…** and **Exit**. WebView2 keeps its native editing shortcuts (Ctrl+Z/Y/X/C/V/A); no clipboard/shortcut proxy is added.                                                                                                                                                                                                                                                                                                                                                                                                  |
| Activity image labels                          | Installed Segoe UI and Consolas from `%SystemRoot%\Fonts`; no fonts are bundled or downloaded. Missing fonts fail explicitly.                                                                                                                                                                                                                                                                                                                                                                                                                           |

## Build from source (Windows x64 host)

Prerequisites: Windows x64, Git, Node.js 22 with npm, Python 3.12 (`python`), Rust 1.98 with the MSVC toolchain (Visual Studio Build Tools "Desktop development with C++"), 7-Zip installed in `Program Files\7-Zip` (used to read, never run, the installer), and the Microsoft Edge WebView2 Runtime. Garmin sync uses the official Personal API in-process; it does not require Python or uv/uvx at runtime.

```powershell
$env:PYTHONUTF8 = "1"   # Python UTF-8 text I/O, as on macOS/Linux
npm ci
npm run desktop:build
```

Builds are native-host only: Windows artifacts are produced and verified on Windows, macOS artifacts on macOS ARM64; any other host refuses. The build downloads and verifies the official checksum-pinned `node-v22.23.4-win-x64.zip`, probes the bundled Node and `better-sqlite3` ABI in memory, builds the locked native app and produces `src-tauri\target\x86_64-pc-windows-msvc\release\bundle\nsis\Garmin Trainer_<version>_x64-setup.exe`. Build identity binds the platform, source, installed dependencies, actual toolchain versions, resource inventory, the installer bytes and its extracted payload.

## Unsigned per-user installer

The installer installs for the current user under `%LOCALAPPDATA%\Garmin Trainer` without administrator elevation, adds Start Menu/desktop shortcuts and an uninstaller. It adds no service, startup entry, updater or login item. It is **unsigned**: Windows SmartScreen may warn about an unknown publisher. Do not disable SmartScreen or other protection to proceed; this project provides no signing or trust bypass.

- **WebView2** is a prerequisite. If it is missing, the installer stops with guidance and installs nothing; it never downloads or installs WebView2 itself.
- **Uninstall never deletes your data.** Settings, databases and tokens under `%APPDATA%\com.codexa.garmin-trainer.desktop` remain until you manage them yourself. (The stock Tauri "delete app data" option is removed.)
- **Program replacement** uses the same install directory and preserves private data; the finite alpha scenario re-executes only the exact same-version installer after owned shutdown and rechecks installed payload/registration/DB/settings before uninstall. Upgrades from earlier public or development installers and downgrades remain unqualified. Installer downgrade refusal in silent/update modes is a contract, not normal-use certification. **Existing-database source-CLI migration is not qualified on Windows**: current maintenance tooling has POSIX uid/mode assumptions. Do not use macOS migration instructions as a tested Windows path. The app never upgrades a database at startup.

## Package and verify without installing

```powershell
$REL = "$PWD\src-tauri\target\x86_64-pc-windows-msvc\release"
npm run release -- package --platform windows-x64 --execute --bundle $REL --scratch <private-scratch>
npm run release -- verify  --platform windows-x64 --bundle $REL --scratch <private-scratch> --record <printed release-windows-x64.json>
```

Use the same `npm run` entry as `npm run desktop:build`: the bound build context includes npm's environment, so invoking `release.py` directly refuses with a context mismatch. Package copies the stamped installer (never rebuilds or relabels it) to `Garmin-Trainer-<version>-windows-x64-setup.exe`, writes its SHA-256 file and a `release-windows-x64.json` record. Package and verify extract the installer payload with 7-Zip into owned scratch after validating every member name, require exactly the producer's binary and resources, x64 PE binaries, the Node license and notices, and the excluded/private-content refusals. The installer is never executed. No macOS size budget applies to Windows.

## On-demand execution

The entire `Windows x64` workflow is **manual-only** (`workflow_dispatch`): PR updates and pushes do not allocate it. Ubuntu Validate and the macOS nightly keep their existing triggers. Windows remains non-required in repository protection.

Select the intended feature branch or main in Actions → Windows x64 → Run workflow, or explicitly dispatch it:

```bash
gh workflow run windows.yml --repo codexa-bh/ai-garmin-trainer --ref <branch>
gh run list --repo codexa-bh/ai-garmin-trainer --workflow windows.yml --event workflow_dispatch --branch <branch> --limit 5
gh run view <run-id> --repo codexa-bh/ai-garmin-trainer --json headSha,event,status,conclusion,url
```

Optional `-f release_export=true` explicitly selects the exact qualified public-safe release triple export below; default dispatch does not export binaries. It grants no tag/upload/publication and changes no automatic triggers.

Before Rust setup, dependencies, resource assembly or native builds, the workflow runs the read-only [rendered disclosure preflight](release.md#rendered-disclosure-preflight) against `release-notes/windows-preflight.json`. That explicit context binds the current notes' Windows selection and prior-release source/schema; it must be reviewed/updated with every cut, not inferred from Latest. Unknown/missing/contradictory context or required alpha/signing/platform/upgrade wording refuses early. Preview placeholders are not artifact identities and do not qualify an installer.

The selected ref is resolved to the dispatch's immutable `github.sha`; checkout and the recorded `TESTED_SOURCE` use that SHA, and the job refuses a different HEAD. Compare the observed run `headSha` with the intended PR head before relying on evidence. A later branch push does not update an earlier dispatch's evidence; explicitly request a new run when needed. Missing automatic Windows PR checks are expected, not a green Windows result.

## Installed-app scenario and narrow evidence exception

After the existing build/package/verify/backend stages, `npm run smoke:windows` consumes that exact verified release record and installer. It refuses non-hosted/non-Windows, dirty or mismatched source, existing registration/program/app-data/shortcuts, aliases, changed payloads and missing WebView2. NSIS runs directly with `/S /NS /D=<exclusive-runner-program-directory>` (`/D` last and unquoted as NSIS requires, including destinations with spaces); it never elevates or downloads prerequisites. Installer/uninstaller processes start suspended inside a fresh invocation-owned kill-on-close Job Object before resuming. The runner waits for the whole tree, including NSIS's forwarded temporary uninstaller child, not just its exiting parent; timeout fails and settles only that owned job. The installed executable/resources must match the verified payload exactly, with only NSIS's generated `uninstall.exe` additionally allowed and bound into native admission's complete installed inventory.

The installed ordinary app uses schema-v2 native admission and run-local private ACL/file-ID/namespace owners, explicit settings/app-data/WebView/temp/DB roots, and an ownership stdin pipe. HOME/USERPROFILE and the normal singleton/settings are never replaced or selected. The existing authored representative recipe is serialized in memory, with no private input. Actual hydrated round trips precede Trainer/Sync/Profile navigation, synthetic controlled-input Goals Save, owned pipe shutdown and restart/readback with fresh capability/boot. Wrong-run/stale-boot access refuses; unrelated Profile fields must remain unchanged. Startup failures report only fixed refusal/runtime-stage enums/booleans, bounded log length and numeric child exit status to CI; own-window creation may additionally report a typed numeric COM HRESULT, never framework text. Raw native logs, paths, settings and capabilities are never forwarded. Validator failure metadata distinguishes only the fixed field/database phase and allowlisted source/SQLite/module failure codes; raw exceptions stay suppressed and the existing UI failure/success semantics do not change. A Windows native contract checks the actual authored-recipe CLI bytes, Python readonly fingerprint/private settings and its live directory pin through native admission, the actual settings validator and nonce-bound owned backend startup/settlement before the expensive installed scenario; it is not installed/UI evidence. The cheaper JS/file-publication preflight runs before native compilation; both remain mandatory. If the Python/native contract's original admission attempt fails, test-only checks distinguish root traversal/privacy/canonical identity from descriptor opening/privacy using fixed stage messages and numeric OS codes only. They never run before admission or retry it, so diagnostic probes cannot warm up the passing path or turn a refusal into success. The native contract uses an unmodified resource copy outside the checkout so ancestor node_modules cannot hide missing packaged dependencies. Pre-entry validator stderr is bounded to 64 KiB, reduced only to fixed loader codes/public module-name enums, then discarded; no raw stack/path/exception is logged or uploaded. Numeric child exit status, bounded stdout/stderr byte counts and a fixed stdout-kind enum distinguish loader/transport from typed validation. The portable native backend contract also runs in a bounded retained no-console child, matching the GUI host's lack of a console without launching default UI. Windows unit-test hosts use an actual GUI PE subsystem, checked directly before the portable backend contract; merely detaching a console from a console-subsystem binary is not equivalent. This test-only linker attribute changes no production/debug-app mode or command privilege. Existing private Settings/history construction remains unchanged: omitting early Settings was tested and did not alter the failure, so that hypothesis was reverted. The isolated single-test GUI child also matches the real runner's private TEMP/TMP before validation/backend startup; it does not mutate the concurrent test harness environment. The native Node boundary uses equivalent DOS spelling for canonical verbatim-drive runtime paths: Node 22's CommonJS main-entry realpath otherwise fails with `EISDIR` at the drive root before validator code runs. Native admission, resource inventory and identity checks keep their original canonical paths; no symlink-resolution or ownership check is disabled. The existing before-use contract now exercises canonical resource paths with spaces and actual validator/backend startup.

Known stderr classifications include fixed Node exception classes only, never exception text. Temporary operator-approved startup excerpts identified the verbatim-drive failure and were removed after the failing-before/passing-after regression established the repair. Settlement observes all WebViews under the UUID-owned run root, including the hidden setup profile.

Six fixed Trainer/Sync/Profile × wide (1280×850) and narrow (420×850) **logical own-WebView** captures use WebView2 `CapturePreview`, the existing hide-by-default geometry-preserving masks and confirmed restoration before private publication. Native diagnostic and image dimensions must agree; unsupported DPI/geometry fails rather than stretching pixels. Every PNG is fully bounded/CRC/deflate/filter-decoded and checked for nonuniform pixels; **these checks do not replace individual visual inspection**. Failure or timeout cannot publish raw pixels.

Only after owned native/backend/profile-WebView/endpoints/writer/namespace settlement does exact same-version program replacement run. The same verified installer is re-executed, payload/registration/shortcuts and synthetic DB/settings/app-data marker must remain unchanged. Then the installed uninstaller runs. The scenario verifies program and uninstall-registration removal, no shortcuts under `/NS`, unchanged saved synthetic DB/settings and an exact marker in the newly owned real `%APPDATA%\\com.codexa.garmin-trainer.desktop` boundary. Stock NSIS retains the manufacturer `Software\\codexa\\Garmin Trainer` install-location metadata; it is inventoried and must remain unchanged, not falsely reported deleted. No unrelated registration/data is adopted or removed. Synthetic state remains only until runner expiry; no primary access or copy-back.

**Task-scoped publication exception:** GitHub Actions may retain exactly the six already-masked synthetic PNGs plus one closed sanitized source/runtime/scenario manifest for **three days**. The pinned upload step names all seven files explicitly. No binaries/installers, DBs/sidecars, settings/keys/tokens, descriptors/capabilities, raw/unverified captures or logs are eligible. A failed/incomplete scenario uploads nothing. This public repository's artifacts must be safe to disclose; three days is requested retention, not guaranteed private access or immediate erasure. All other smoke images, including macOS captures, retain their no-upload rule. No release, image mirror or broader standing exception follows.

Download the exact run/attempt/source artifact, treat the archive/manifest as untrusted, verify the exact allowlist/hashes/identity, then **open each of the six images individually** and record durable textual state/layout/masking/defect findings before expiry. ## Proposed manual development feedback path (design only)

There is **no implemented fast mode**. Both values of `release_export` in `windows.yml` still run the complete installed-app qualification; false only omits the separate binary export. Do not relabel build-only or older feedback as release evidence.

A future implementation would add a separate `windows-dev.yml`, explicitly named **Windows development feedback — nonqualifying**, with `workflow_dispatch` only and no required-check, PR/push/schedule or workflow-call trigger. The dispatch-selected ref resolves once to immutable `github.sha`; checkout/HEAD and the summary must agree on that exact SHA. It would use Windows Server 2025 x64, the existing pinned Node/Python/Rust inputs, contents-read, no secrets/private services, fresh per-job state, and only the existing lock-keyed npm download cache. No shared writable build output or verification cache is proposed.

The useful bounded workload would be: prerequisites/toolchain facts; locked `npm ci`; release/disclosure/identity/private-file/process contract tests; production backend/resource assembly and pinned Node/SQLite probe; focused platform/ownership/renderer JS tests; locked native Windows tests against those resources; and the synthetic packaged-backend smoke. It should report each actual stage/outcome and creation-to-verdict, queue and runner-time observations, with failures/skips/unavailable coverage distinct. A finite timeout stops work rather than silently falling back to a smaller success profile.

It would **omit** the full ordinary release build and NSIS installer, stamped producer admission, package/extract/final-installer verification, installed payload admission, installed hydration/navigation/Goals save/restart, same-version replacement, preserving uninstall, six restored masked images/visual review, release-record/set assembly, export/import/provider archive verification and publication. Resource assembly alone confers none of these properties. Real services, normal onboarding, trusted native input/chrome and Windows 11/ARM remain unqualified.

Separation is structural: no `release_export` input, no artifact upload or release/candidate/qualification output, no package/export/publication commands, and no minting of a successful installed-scenario manifest or release record. Its summary must always say **Development feedback only — not release qualification**; passing development steps cannot change that statement. Full `windows.yml` qualification on the exact final installer, current source/run/attempt identities, strict downloaded artifact validation and individual image inspection remain mandatory for release eligibility. A development run cannot donate status, receipts, images or provenance to that path.

Before later implementation, tests must prove manual-only least-privilege routing, immutable selected-source handling, positive enrollment of the useful workload, and absence/refusal of export/publication/qualification routes and `release_export`. Existing release export consumers must reject its workflow identity, missing installed manifest and forged or copied qualification claims. Integration evidence must observe the new path's honest failed/skipped summaries and show that only a separate successful full workflow can produce an eligible installer. This section authorizes no implementation, dispatch or new workflow by itself.
