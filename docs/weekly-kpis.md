# Structured weekly KPIs

KPIs remain weekly commitments managed in trainer chat, not a separate goals catalog or manual editor. Weekly documents explain intent/reasons; structured sets and assessments are the saved value authority. Existing narrative bytes/revisions remain preserved sources. General Plan editing is unchanged.

## Identity and saved meaning

A first planned set is the immutable original, even if saved before the week. Adaptations get new IDs; assessments bind exact set/item/track references, never an implicit latest target or narrative review.planRevision. A legacy recorded plan may receive an explicitly **review-defined, provisional** interpretation through chat; it does not acquire a fabricated agreed original. Historical commitment editing remains disallowed; assessment corrections replace only that set's current assessment revision. Stored versions remain intact, but report, trainer review and achievement use the latest committed target set only. A later correction of an older assessment never replaces the latest plan's score. Optional set.planRevision records explicit narrative provenance; review-defined eligibility requires it to match the latest narrative revision, never a timestamp/prose guess.

Items have stable concept IDs and one to three named numeric/qualifying tracks. Count and duration can share one point allocation. Target and available points are independently optional; monitoring/context does not default to scoring. A concept/track key must retain exact kind/unit/meaning; changed semantics require a distinct identity. Labels and targets may change without silently changing units. Unknown is null, not measured zero. Evidence origin/references and cutoff remain required saved facts, not fresh Garmin verification. Qualification/limitations and result explanations are optional, for necessary uncertainty or actual substitution/partial-credit meaning only. Ordinary targets/points need no duplicate prose. Optional scoring records a non-obvious agreed rule needed by later trainer assessment (for example, an agreed reduced award for a substituted session); it is not evaluated by code. Real extra-credit explanation remains required to explain its relevance. Legacy definition/selection/evidenceRequired/provenance/overall explanation bytes remain accepted and stored, but are absent from new model-generation schemas.

The trainer preserves the100-point full-achievement convention, explained useful bonus/partial credit (including above100), latest-plan denominators, unmet sport-specific commitments and explicitly provisional assumptions. Before equivalent future writes, bounded context latestPlanWeek and getKpiProgress.latestPlan expose the canonical names, concept IDs, keys and exact meanings to reuse; harmless label/target changes do not create a new identity. Genuinely different selection/qualification/unit semantics remain distinct. Code validates structure/references/finite values; it does not judge eligibility, select activities, award/cap points, infer targets from results or evaluate on view/sync/rollover.

## Reads, writes and limits

- getWeeklyPlan returns narrative plus canonical KPI data. getWeeklyKpis reads original/latest/review-defined or one explicit retained set ID. complete=false carries safe narrower set IDs, never editable preview authority.
- One complete relevant prior-pass read, unchanged overall KPI revision, matching civil week/calendar and current-turn ownership are required. A narrower read includes the complete selected set/assessment. Presentation automatically narrows an incomplete envelope to the latest eligible set; refresh does not pin an obsolete selected set.
- saveWeeklyKpis performs a focused single-week change. saveWeeklyDocuments.kpiChanges commits related narrative/KPI/assessment changes in one synchronous SQLite transaction, at most two distinct weeks. setId=new binds only to the same-operation new commitment. No provider/semantic extraction awaits inside a transaction.
- Focused/combined weekly mutations share one attempt per turn, including failed/uncertain attempts; General Plan has its separate attempt/outcome. Reread/reconcile uncertainty, never replay. Both JSON and NDJSON successful metadata refresh saved weekly/Progress views.
- Sets: at most12 items,3 tracks/item,24000 serialized characters/set or assessment; up to128 immutable sets/week. Assessment corrections retain exact set identity with a fresh assessment revision. Read evidence is at most60000 characters; a single selected object omits archive metadata to remain complete. getKpiProgress reads at most12 civil weeks; oversized tool evidence explicitly asks for a narrower range. It grants no write authority.
- One weekly-owned read-only projection selects latestPlanSetId and its exact assessment for both compact report and primary achievement chart. It uses saved finite total / positive sum of scored-item allocations once per item; monitoring adds nothing and extras already in the total are not added twice. Missing/incomplete/unavailable totals or denominators are gaps, true zero stays zero, and explained above100 is not capped. No assessment/save occurs on read.
- Progress carries only each week's latest eligible set; latestPlan is discovered separately by a persistence-owned latest-established-plan query, not by the chosen range or assessment time. Empty future slots do not replace it; a real KPI-free plan has no resurrected historical choices. Secondary measurements join exact concept/key/kind/unit/meaning through each week's latest set, retaining its target/actual/cutoff association. Labels/target amounts may differ; conflicting or incompatible observations stay unavailable. No fuzzy renderer matching or global baseline control.

The report table has one **numeric measurement per row**, with its own target/actual. Scored commitments (including zero allocations) and saved extra credit precede monitoring-only rows; each group's stored order is preserved. Numeric tracks of a compound commitment use disambiguating labels; a scored commitment's existing allocation spans its measurement rows once, explicitly marked Shared. This does not invent per-track weights or change saved totals/denominators. Qualifying/boolean tracks are conditions/evidence, not normal KPI target/actual rows. Any condition-only legacy allocation remains explicit as a concise conditional-points annotation beside the grid and in its original saved total, rather than disappearing or becoming a Yes/No metric. The redundant Scoring and evidence section is removed.

Individual Progress opens by default and renders every latest-plan numeric track, with distinct labels/units for compound and same-unit measurements. There is no selection step, Week details navigation or Saved measurement values panel. Focusable chart-local figures provide nonvisual exact values, status/cutoff and necessary qualification without replacement visible tables. Qualifying/boolean tracks remain saved conditions and evidence context, not standalone chart series; omitting them from charts never removes their role in an agreed assessment. Measurement charts compare the lower/equal target with recorded actual from a zero vertical baseline. A range upper bound stays preserved in report/text but is not a separate plotted or tooltip series. Current week / Next week notes open at full grid width; History reverses the notes order (Review before Plan) and keeps both closed, including narrative-only records. Compact scoped titles and a viewport-bounded flex parent account for wrapped tabs; content children cannot shrink into a clipped pane. Routine Reload is removed from weekly/General Plan success states; navigation/save reads, drafts and failure-only Retry retain their owners. Calendar and report routing are unchanged.

## Storage, migration and recovery

Schema26 adds weekly_kpi (week-bound JSON state) and weekly_kpi_track (unique concept/track signature). The weekly application owns internal reference validation; SQLite owns atomic storage. The existing lazy connection is shared; no eager resources, startup semantic extraction, new SQL analytics access or deletion authority. KPI-only data triggers user-data/backup detection and survives chat/Profile and Garmin deletion. Fresh initialization includes26; schema25 native builds refuse26 and schema26 existing-data admission refuses25 until explicit maintenance.

Historical backfill is a finite **reviewed mapping**, not a Markdown parser or LLM job. Under separately authorized exact source read/copy scope, inventory original/latest/review bytes privately, review every mapping, rehearse on a WAL-consistent disposable copy and verify integrity/FKs/references/coverage and unchanged source/unrelated rows. KPI-free/unassessed/ambiguous history stays absent or explicitly unresolved; never create missing targets, agreement, scores or interpretation. Preserve recorded review-only and retained versions, compound/exclusion and conditional evidence semantics; preservation does not imply showing obsolete comparisons.

For an approved stopped target with a genuine recoverable pre-upgrade backup and compatible artifact/activation plan:

1. Explicit process-env DATABASE_PATH with npm run db:migrate performs writer admission and schema DDL only. It preserves explicit fresh-target initialization, requires a canonical selected path and existing canonical parent, refuses fresh sidecar collisions, and creates populated/upgrade sibling backups exclusively in a canonical owner-private backups directory. SQLite online backup includes committed WAL; the owned backup is made standalone DELETE-journal and integrity/FK/version verified before DDL. Partial failures retain output; no automatic restore/downgrade or lease stealing.
2. npm run backfill:weekly-kpis -- /absolute/private/reviewed-manifest.json uses the same explicit process-env target and writer owner, requires current schema, verifies source byte hashes and complete source identity, and transactionally applies/reconciles the finite mapping. Manifest v1 is {version:1,mappings:[{sourceSha256,source,state}]}; source is the exact WeeklyRecord and state is reviewed WeeklyKpis with durable IDs. Keep it bounded (4MiB), owner-private and outside public assets. Existing matching state reconciles; changed source or conflicting state refuses without partial writes.
3. Verify all target facts again, then only the separately approved compatible activation/reopen. After new writes prefer forward-fix; restoring an old backup needs reconciliation of newer writes and separate authority. Source merge, rehearsal and lifecycle Done grant no installation, stop/reopen or production mutation.

### Existing-state source binding (no schema upgrade)

When a separately approved inventory confirms recorded source relationships but older sets lack explicit metadata, use the distinct finite `npm run reconcile:weekly-kpi-sources -- /absolute/private/manifest.json` with explicit process-env DATABASE_PATH on an approved stopped target/copy. Manifest v1 has mappings `{sourceSha256, source, expected, newRevision, planRevisions}`: exact narrative bytes/record, complete expected structured state, a fixed new conflict revision and reviewed set-ID → narrative-revision bindings. Planned sources bind original; adapted/review-defined sources bind latest. This operation only appends planRevision metadata and changes the conflict revision; it never overwrites identities, signatures, labels, values, targets, scores or narrative. Identical rerun reconciles; newer/mismatched source/state or incompatible existing binding refuses atomically. Existing backfill retains its conflict refusal and has no overwrite flag.

Rehearse preservation, idempotence, changed-source refusal and rollback/forward recovery on a WAL-consistent disposable copy first. Reusable identity/signature equality may make identity reconciliation a verified no-op; do not merge restricted-window, selected-outing or changed qualification semantics merely because labels resemble each other. No alias/classifier platform is introduced. JSON metadata is additive within schema26; no DDL, automatic startup repair or historical rescoring. Production application, compatible activation and recovery remain separately authorized; source delivery does not install anything.
