# ChatGPT subscription access

ChatGPT subscription and **OpenAI API key** are separate optional providers. The local, public-source desktop app uses OpenAI's documented [Sign in with ChatGPT flow](https://developers.openai.com/siwc/token-sharing-open-source). It does not borrow Codex credentials, require a partner key, add an app-access login or automatically switch to paid API billing. Eligibility, supported models and plan/credit restrictions are determined by OpenAI; remotely hosted/commercial use has separate requirements.

## Connect and choose explicitly

1. Open native **Settings → ChatGPT subscription**. There is one active connection, reused without signing in again. Use **Continue with ChatGPT** initially. **Switch account** first opens **Account to use**: choose a retained connection, then **Continue with selection** to authorize its existing issued client in your private system browser. **Back** makes no connection change. Choose **New account/workspace** only for an intentionally new registration; it is not a way to reconnect or discover an already-saved account. A failed/cancelled switch leaves the previous connection active. Old private records remain inactive for recovery until deliberately selected and verified, not extra connected accounts. If an older installation has several saved registrations, a one-time **Connection to keep → Use this account** choice resolves that ambiguity without choosing the first row. Never paste passwords, tokens, callback URLs or authorization URLs into chat, logs or issues.
2. A signed-in identity is not necessarily plan-use permission. If Settings reports identity-only access, use **Enable plan permission** deliberately. Declining/cancelling preserves prior saved connections.
3. Use the saved registration, then **Refresh models**. Only that registration's visible model catalog is offered. Account changes clear add-picker selections; no model is selected automatically. Switching never rewrites catalog, Trainer or summary/title identities: old-account choices become unavailable until explicitly replaced. Returning authorization selects the saved issued client and host before opening the browser and verifies the original identity/client before replacing credentials. It never creates a fresh client just to look up a saved identity. Separate issued clients may represent different workspaces even for the same subject/email, so an explicit new registration is never merged by those labels. An explicit retained selection resolves duplicate recovery records; ambiguous legacy records require the one-time choice. No records are silently merged, deleted or remotely revoked, and matching email labels are never identity proof.
4. Under **Models to add**, check new models (or **Select all**) and **Add selected** once, then **Save settings**. The count is only new selections to add, not saved membership. The catalog rows below contain saved models and any unsaved catalog edits; Save commits those edits and Cancel restores the saved rows. Already-added account/model pairs are hidden from the add picker; when every model is already in the catalog, the picker and Add selected controls are hidden. Existing catalog rows remain available for explicit removal. Reopening Settings preserves saved rows without checking them again; Cancel discards catalog edits. The full batch must fit the 32-model catalog limit or nothing is added; deselect models or remove draft rows first. Connection credentials are saved independently of catalog drafts. Cancelling a catalog edit does not roll back an already committed connection.
5. Choose the exact **ChatGPT plan / model** entry in Trainer. The active connection needs no account-number prefix. Legacy unavailable identities remain distinct and are never substituted. The shared **Memory and automatic chat-title model** is a separate explicit choice in Settings; connecting a subscription never retargets an existing API-key choice.

The first successful plan-enabled connection displays the plan/credit disclosure once. Trainer identifies the subscription billing route and offers **Manage usage**, which opens the fixed official ChatGPT usage destination. Requests can consume plan usage or credits: this is not a free/unlimited allowance, API token-price invoice or remaining-quota estimate.

A failed chat reports a closed category when available, such as `connection_unavailable`, `http_403` or `response_decoding_failed`. Existing per-call local debug records optionally retain `failure`: category, observed stage, bounded monotonic elapsed milliseconds, validated HTTP status and a fully validated response `x-request-id` when available. Stages distinguish `upstream_request`/`upstream_read`, `stream_validation`/`sdk_decode`, `native_credential`, `native_poll`, `native_final_current`, `local_admission` and `aborted`; otherwise `generation` remains unknown. A failed final native current check still rejects an otherwise completed stream. These are observed boundaries, not proven network/authentication root causes or reconnect advice.

An `incomplete_sdk_decoding` failure at `sdk_decode` may additionally retain a closed `receipt` comparison: `absent` (no validated terminal receipt), or `present` with independent text (`match`, `observed_empty`, `receipt_empty`, `observed_prefix`, `different`) and call (`match`/`mismatch`) results, observed and receipt call counts, and the canonical call dimensions that differ (`count`, `order`, `id`, `name`, `arguments`). Values are compared only in memory; the record never contains text, arguments, IDs or hashes, so equal-length differences are detected without revealing them. An invalid or unknown receipt value is omitted whole.

SDK text delta/end without an active matching text start is `sdk_text_lifecycle_failed` at `sdk_decode`, not a copied dynamic error containing the item ID. Missing message IDs, unsupported phases or rotating identities can lead to this observed lifecycle failure; the category does not prove which upstream cause occurred. A failed call may also retain canonical bounded `dropped` counts for `response.output_item.added`, `response.output_item.done` (message/function-call branches) and `response.output_text.delta`. These count actual locked-SDK fallback outcomes after decoder translation, not approximate schema checks, app-side refusals or unknown future event kinds. Raw chunks stay in memory. Observed drops alone do not reject an otherwise exact result.

Optional `responseCorrelation` is separately labelled `source:response.created`, never interchangeable with `x-request-id`. The supported whole-value subset is `resp_` plus exactly 32 lowercase hexadecimal digits, demonstrated by the [public OpenAI Responses cookbook](https://github.com/openai/openai-cookbook/blob/main/examples/responses_api/responses_example.ipynb). Other formats and conflicting created identities omit correlation whole. This intentionally conservative subset is not a universal provider-ID promise, authentication check or root-cause proof.

The same projected value can be retained on a failed summary attempt and shown in Trainer **Memory → Provider failure details**, collapsed by default. Old failures have no reconstructed detail. See [paused summary recovery](memory.md#paused-summary-recovery).

Unknown provider codes become `request_failed`; no raw error text, causes, bodies, prompts, tokens, account labels, paths or credential details enter this projection. Invalid or overlong IDs are omitted whole, never truncated into accepted IDs. Missing metadata stays absent; older rows have no field and existing JSON caps may omit diagnostics. The original 2026-11-17 `stream_interrupted` incident discarded its cause: these future diagnostics cannot recover it. Inspect the bounded failure record rather than replaying requests or reconnecting blindly. Full debug traces can independently contain private chat/tool context and are **not** shareable support bundles.

Catalog/key Save uses the existing live acknowledgment. A successful connection also updates the owned backend's secret-free availability metadata. Saved/not-applied or unknown results do not mean rollback or permission to retry blindly: reload to inspect saved state, and explicitly quit/reopen when activation cannot be confirmed. Ordinary Save never restarts the backend. Other startup-only settings remain restart-only.

## Recovery and lifetime

- **Signed in, plan permission required**
  - Deliberate next action: Enable plan permission; do not assume identity access authorizes inference.
- **No account model selected / stale or removed model**
  - Deliberate next action: Refresh the selected registration's catalog and choose a supported entry explicitly. Old preferences remain visible/unavailable, never substituted.
- **Reconnect required / terminal refresh rejection**
  - Deliberate next action: Continue with the selected saved registration; its issued client and verified identity must still match.
- **Interrupted new registration, known issued client**
  - Deliberate next action: Retry deliberately using the retained issued client and host, including after restart. No automatic authorization or code replay.
- **Interrupted new registration, unknown remote effects**
  - Deliberate next action: Preserve local state and reconcile the intended connected app with the operator before another new registration. Do not delete private files or blindly retry.
- **Transient network/service failure**
  - Deliberate next action: Retain the connection and inspect/retry deliberately. There is no sign-in loop or automatic inference replay.
- **Usage limit**
  - Deliberate next action: Manage usage. The failure does not establish whole-plan exhaustion or a reset time. API-key routing requires a separate manual selection.
- **Ineligible account, region, route or capability**
  - Deliberate next action: Check current OpenAI eligibility/model support. Repeated sign-in or a paid fallback is not an automatic remedy.
- **Private connection state unavailable / unsupported**
  - Deliberate next action: Preserve originals and use a compatible build or reconcile private storage. Do not delete/chmod/adopt files to bypass refusal. Other configured API-key/local routes remain independent.
- **Saved/live activation unknown**
  - Deliberate next action: Inspect saved state and explicitly reopen if necessary; do not treat a timeout as rollback or a confirmed live update.

ID-token audience validation accepts the issued client as either a string or a single-element string array, as defined by [OpenID Connect](https://openid.net/specs/openid-connect-core-1_0.html#IDToken). An explicit authorized-party claim must match that issued client; multiple audiences retain the additional matching-party requirement. Signature, trusted issuer/key, original nonce, expiry and returning-registration identity checks remain mandatory.

Identity-validation failures preserve the previous connection. A parenthesized category identifies only the rejected check (token format, signing header, issuer, account identity, issued client, token time, sign-in nonce, trusted signing key, signature or saved registration), never the token or its contents. Unknown categories retain the generic failure. Report only that category and the source/build version; never copy callback URLs, browser addresses, credentials, raw claims or private account labels. The browser's “Return to Garmin Trainer” acknowledgment means a callback was received, not that identity validation or connection commit succeeded.

A model-discovery failure is separate from sign-in success. Closed categories distinguish network/service refusal, rate limiting, a bounded-response/size refusal, unsupported catalog metadata and duplicate models without exposing response bodies or credentials. Model catalogs may include substantial provider metadata: their network read has a separate 2 MiB hard bound, while credential/discovery reads retain 128 KiB. At most 256 catalog records are accepted and only validated visible model IDs/display names are projected; extra metadata never reaches Settings or evidence. The saved connection/catalog is preserved on failures; an unavailable result does not mean the account has no supported models. Reload status before a deliberate retry, and do not disconnect or sign in repeatedly to diagnose it.

Authorization is bounded to three minutes. Cancel/Settings-close/quit invalidate the captured native attempt, including queued or late results. A stale Cancel cannot cancel a newer attempt. Token rotation is serialized and atomically saved by native ownership; transient failures do not erase credentials. Changed plan permission or model entitlements invalidate the affected account's older admissions; unchanged discovery and token-only rotation preserve them.

**Disconnect** invalidates local access and clears local tokens before attempting renewable-session revocation. The issued-client/account mapping and host identity remain for deliberate reauthorization. A remote revocation failure is reported separately; manage access in ChatGPT if confirmation is unavailable. Already committed local tool writes remain committed, and interrupted/unknown effects are not silently replayed. Unrelated providers retain their captured settings.

## Keep one intended connected app

1. Reconnect the intended **retained** connection, never the New account/workspace option. Privately inspect the actual ChatGPT connected-app list before and after reconnect and after reopening the ordinary app; the count must not grow. Do not send credentials, URLs, client IDs or account labels to an assistant.
2. Identify the intended entry using details in the provider's **Sign in with ChatGPT** management screen, when available. Names, list order and usage percentages are not identity evidence; local ordinal labels distinguish saved records, not remote entries. If the details do not distinguish identical entries safely, defer cleanup rather than guessing.
3. Remove/revoke only identified obsolete entries yourself if the provider exposes that control. Turning off an allowance under **Connected App Limits** is not deletion. Revoking the retained entry interrupts its access; this app never deletes or merges remote entries automatically. After cleanup, confirm one intended entry remains and another deliberate retained reconnect adds none. Deferred cleanup is not a completed one-entry outcome.

## Private boundary and compatibility

Native code owns an original-preserving versioned companion record beside private Settings, with owner-private directories/files, pinned no-follow reads, cross-process exclusion and atomic publication. Before any first-registration authorization, it durably records optional v2 `pendingAuthorization: {clientId: null}` to fence unknown remote effects. A known issued client is retained on helper failure or before credential publication as `{clientId: <issued client>}`; deliberate retry reuses that client. Success clears this marker atomically with credential publication. A cancelled process before a known result may leave an unknown outcome; it refuses fresh registration rather than claiming rollback. Existing v1/v2 documents need no migration, and older deny-unknown-fields readers refuse extended documents while the marker is present. Do not downgrade, delete files or copy credentials to evade this refusal. The current `chatgpt-v1/records/credentials-v2.json` records the active registration and retained recovery records. Newest-file presence is authoritative, including unsafe or unsupported objects. Existing `credentials-v1.json` is read without migration: a sole connection resolves read-only; multiple connections are unavailable until explicitly chosen. The first successful native write exclusively publishes v2 and leaves v1 bytes unchanged. Archived records cannot obtain credentials, refresh models or service captured admissions; a switch fences old epochs. Retained record capacity remains bounded at16, with refusal rather than automatic deletion when full. Use a compatible forward build, not an older writer/downgrade or file deletion; older installed builds may not recognize v2. Storage is **plaintext, not encryption**: same-user/privileged processes and backups can read it. No secure-erasure guarantee is made. Unsupported/unsafe records refuse without downgrade or overwrite.

Only trusted native Settings can authorize or administer a connection. Renderer/model/tool/SQLite history/job/support data receive no tokens, raw claims, issued client IDs or credential paths. The owned backend receives a private startup capability, not a renderer credential. OAuth/network helper input/output use private pipes; ID-token hints do not enter process argv. Connector/FIT children receive neither provider secrets nor subscription account metadata.

The private Node-to-native broker uses a fixed loopback HTTP request, not browser Fetch (which adds `Sec-Fetch-Mode` even in Node). Native browser-header refusal remains mandatory. The client retains capability/exact-operation/epoch binding, cancellation/deadlines, bounded responses and no redirect or cache. A currentness check may retry one pre-response wire failure within its original five-second deadline; it must still receive authoritative current confirmation. Credential acquisition, native refusals, malformed responses, inference and tools are never replayed by this recovery.

Existing settings/catalog entries and API-key summary encodings remain compatible. Subscription entries additionally bind an opaque local registration; shared summary/title selection uses a closed version-2 identity. Older readers refuse the new provider instead of downgrading it. Startup activation wraps the prior frame in version4; current credential records are version2 with original version1 compatibility as described above. There is no SQLite schema migration, Garmin backfill, historical accounting rewrite, private-file import or primary cutover for this provider addition.

## Inference behavior

Every applicable subscription purpose uses selected-account OAuth at the documented public streaming Responses endpoint: coaching/planner/synthesis, namespaced local tools, linked history, supported local compaction, independent summaries/maintenance/rebuild/import/Densify and automatic titles (including Summary Off). Full required history and saved memory remain client-supplied. Ordinary coaching does not restart retired vector extraction/embeddings or require API keys/a separate token-count endpoint.

The adapter omits unsupported direct-API presets and stored-conversation continuation. Private inference explicitly requests SSE and disables fetch caching. Success requires a completed terminal stream and exact locked-SDK text/tool receipt, not HTTP200, a text delta, MIME metadata or EOF. The Responses protocol makes a `function_call` output item `id` optional, while the locked SDK otherwise silently drops such a call; after the namespace/tool/status checks pass, the adapter gives the SDK decoder that item's own `call_id` as its reference ID. The provider's call identity, name and arguments are unchanged and must still exactly match the terminal receipt. The subscription backend's `response.completed` event may also carry no `output` (OpenAI's own Codex client likewise reads results only from `response.output_item.done`). When the terminal output is absent or empty, the receipt is built from those completed output items in `output_index` order, after the same namespace/tool/argument validation. Duplicate or out-of-range indexes refuse. This is still an independent comparison: the SDK's text comes from deltas, and the receipt's from completed items. A nonempty terminal output that disagrees still fails. An absent Content-Type still requires the same bounded closed SSE, completion, namespace and current-account validation; explicitly non-SSE media, JSON bodies and merely stream-looking prefixes never become success. Malformed/partial/incomplete/failed/quota/interrupted output stays failed; local effects and missing usage counters remain truthful. Diagnostics add no provider/tool call, retry, reconnect or paid fallback. No automatic paid fallback or generation repair/replay is added. Subscription tokens are observed when returned, never multiplied by API prices or labelled $0. Selected activity-image analysis remains unavailable until that route/model capability is verified.

## Verification boundary

Deterministic tests exercise production composition and serialized HTTP/SSE with authored credentials. A loopback fixture separately tests the actual private Node HTTP client, Fetch's browser headers, response bounds and cancellation; native tests cover the production protected-storage/refresh/cancellation/admission guards. Locked-SDK stream, structured-purpose, incomplete and tool-safety cases run with declared and absent media metadata. Debug and release-probe builds cannot open a ChatGPT credential owner, create a host namespace, discover models, authorize or revoke a real account. Routine ordinary smoke also retains its isolated keyless denial; it never borrows the normal app's credentials. The finite keyless [Settings presentation scenario](smoke/settings.md#finite-chatgpt-settings-presentation) verifies native layout and actual form controls, including saved-versus-new intent and Back, using fictional secret-free metadata, without a credential owner or provider request. None of those certifies an eligible real account, browser authorization, real token renewal or billed inference.

Actual integration requires an eligible saved connection (or explicitly arranged private operator sign-in when needed), bounded subscription-usage permission, authored app data and a noninterfering native window. The operator enters credentials privately. Record that exact service proof—or its unavailable boundary—separately from synthetic/native presentation. Source delivery does not install, restart the normal app, release or authorize primary-data use.
