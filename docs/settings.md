# Settings, model choice and memory options

User guide to native Settings and the chat model selector. Storage, adoption and the private settings protocol are specified in [desktop runtime](desktop.md#explicit-private-state-adoption); Garmin key handling in [Garmin connection](garmin-auth.md).

## First run and Settings

First launch opens **Settings**, also available from the native app menu even without a working backend. Desktop no longer loads/selects/discovers env files or its old configuration pointer. Upgrading users must re-enter settings; original env files, DBs and old Garmin token files are not imported, moved, changed or deleted.

A genuinely blank installation opens a guided **Data → Provider → Connect Garmin or continue → Review** wizard. Explicitly choose **Create new database** (unused destination only) or **Use existing data** (compatible SQLite only). Native proposes an owner-private platform app-data destination outside the checkout. No history date is required: explicit Sync starts with recent data and continues older discovery in bounded batches. Under **Garmin history**, enable **Limit how far back to import** only to choose an explicit **Import from** date. The date is hidden while Off; turning the limit off and saving returns to automatic discovery after quit/reopen. Create new initializes the authoritative current schema in memory, then exclusively publishes the new file without overwriting files, sidecars or leases. Existing selection and ordinary startup never create, migrate or adopt a missing/old/corrupt/owned database.

Use canonical absolute paths, not aliases, shell expansion or cwd-relative paths. Custom new destinations need an existing owner-private parent. For existing data, first evaluate on a WAL-consistent populated disposable backup. Choose Connect Garmin or Continue without Garmin; configured-provider chat and saved/offline history do not require Garmin.

Provider keys are entered only in the local settings window and stored by native code in an **owner-private plaintext settings file** (folder `0700`, file `0600`). This is not encryption: the same user, privileged processes and backups can read it. Reads show masked status, never saved values. Untouched fields keep prior keys. A fixed mask indicates saved presence, never the key’s length or value. Type or paste to replace; Backspace/Delete on the mask marks removal, applied only on explicit Save. Legacy Keychain settings require explicit one-time **Adopt referenced Keychain keys once**, or private re-entry of every configured slot. Startup/reads/saves never access Keychain; denied adoption does not auto-retry. Original settings and Keychain items remain unchanged. See [storage and recovery](desktop.md#explicit-private-state-adoption). **Memory → Remember across chats** controls startup configuration, not deletion. Choose the shared memory/automatic-title model and memory size separately from Trainer’s chat model. Save, then explicitly quit/reopen to apply memory changes. Saving On does not undo an immediate Disable in Trainer → Memory. Legacy configuration and custom executable overrides remain preserved internally, without technical editors or a diagnostic status section in normal Settings.

- **Chat model catalog** separates ChatGPT subscription from OpenAI API key, DeepSeek, Ollama and OpenRouter. One active ChatGPT connection has explicit Switch account; legacy multi-connection state requires a one-time choice and old records remain private for recovery. Subscription rows bind that exact registration and account model; other providers retain compact exact Model IDs and shared key controls. There is no configured default. Existing API-key/Ollama labels use provider / exact Model ID only; valid old names remain inert, round-trippable compatibility metadata with no name editor. Trainer remembers one explicit choice per selected SQLite DB. Keys are shared once per provider; no discovery or automatic fallback. New configurations require an explicit chat choice, even with one eligible entry.
- Ollama has equal catalog prominence; its loopback endpoint stays Advanced. Manage its daemon/models separately. OpenRouter remains explicit opt-in; review [privacy and tool-reliability limits](local-runtime.md#opt-in-openrouter-chat).
- Explicit Save retains original settings and exact prior-choice compatibility inputs before retiring old defaults. Legacy auto projects only its determinable prior DeepSeek-first/OpenAI-by-key selection, never continuing failover. Extraction/title compatibility and embeddings stay independent.
- **[ChatGPT subscription](chatgpt.md)** uses native Continue with ChatGPT, private system-browser authorization, explicit account models and plan/credit accounting, without an OpenAI API key or borrowed Codex credentials. Connection commit and catalog Save are separate; no automatic paid fallback.

On a genuine first run, **Finish and open Trainer** validates local settings/required keys, saves private file settings and starts one verified owned backend in the same session. This proves local configuration, not remote funding/model/network availability; there is no provider probe, automatic fallback or automatic Garmin sync/login. Ollama remains separately managed. If setup fails, read the reported commit state: a published DB, saved settings or independently verified tokens are retained, not rolled back. **Retry opening saved Trainer** uses the committed configuration only; after interruption before settings commit, explicitly select the retained DB with Use existing data.

For an existing installation, **Save settings** commits privately, then live-applies only chat catalog and shared provider-key changes to the owned running backend. Confirm the reported result: Applied, saved/not applied, or saved/live outcome unknown. Reload reconciles active versus saved state without retrying Save. Other settings (including DB/Garmin account, endpoints and memory topology) still need explicit quit/reopen. A confirmed Save that changes effective startup-only settings still pending activation shows a dismissal-only **Restart required** dialog. Unchanged/repeated and live-only Saves do not repeat it, even with older pending changes; restoring active values does not require it. Dismissal never restarts the app. Ordinary saves never start/restart a backend or switch a live DB/Garmin account. Invalid/unsupported saved settings are preserved, never treated as blank-install authority. The trainer's independently saved model preference is preserved.

## Garmin access in Settings

Create a **Personal API key** in Garmin Connect (Settings → Personal API key) in your own browser, then choose **Connect Garmin** in trusted native Settings, paste the key and **Save** (first run: **Finish**). Explicitly quit and reopen to use it; Save never switches a running connection. The key is stored owner-private on this device (plaintext, not encryption) and never shown again, logged or sent to AI; keep it out of chat, screenshots and issues. Existing installations from the earlier unofficial connector show **Reconnect needed**: their saved history stays available and old token files are left untouched. See [connection and key handling](garmin-auth.md). Sync also imports sleep sub-scores, HRV baseline, VO2 max, Body Battery, stress breakdown, per-lap HR zones, running dynamics and snowboarding summaries for the trainer; existing history gains them only through an explicit backfill ([additional Garmin data](garmin-extra-data.md)).

Settings shows **Key saved** or **Not connected**, never key validity. **Sync → Garmin maintenance → Verify connection** is the only explicit check. Failures are reported at the requested action as a rejected key (create and save a new one), rate limiting or network/service unavailability (retry later), with no automatic retry. Saved/offline data remains usable without Garmin, and native Settings remains reachable from the app menu even without a backend.

Garmin reads are read-only HTTPS requests to the fixed official origin with memory-only bearer tokens; activity files are decoded in-process. Garmin enables fresh Garmin data/coaching but does not gate chat or offline history. No app-access sign-in is required; Garmin access/sync is never automatic at startup.

## Trainer model selector

Trainer navigation uses **Profile & data** for editable Profile, imported athlete/body facts, diagnostics and deletion. **Sync** owns explicit connection verification, import-summary refresh and activity-detail maintenance; Memory remains separate.

Chat's compact **Model** selector (accessible name **Trainer model**) lists locally eligible activated catalog entries with provider/exact-ID labels. Missing-key cloud entries are omitted; eligible keyless Ollama entries remain. An unavailable selected identity stays explicit, never visually or persistently replaced by the first eligible choice. With no eligible entries, configure provider keys/models in native Settings, confirm live application and retry availability. Saving an eligible identity affects subsequent trainer turns without restarting; running turns retain their captured model/configuration. The app-wide preference persists across reloads/restarts. There is no Default/Reset action. Deleted/missing-key/invalid choices stay unavailable until explicitly replaced, with no provider-only remapping or silent substitution. One-time durable compatibility preserves prior exact saved/legacy/default intent without overwriting original preferences; a new configuration remains unselected.

Eligibility means local configuration, not account funding, installed models or remote readiness. The chat control never exposes/edits keys or changes the shared summary/title selection. Native Settings owns private updates; catalog/keys can apply live after exact acknowledgment. Captured chat, memory and deferred-title work retain their admitted credentials; other configuration stays restart-only. See [local runtime](local-runtime.md#runtime-trainer-model-preference).

## Cross-chat memory and debug traces

Native Settings → Memory offers **Remember across chats** (default Off), **Memory and automatic chat-title model** (default Unselected) and **Generated summary target (characters)** (default6000, range1000–20000; advisory generated-text guidance, not a maximum; preferences separate). Choose an exact configured catalog entry independently of Trainer chat; minimized context may leave the device through that provider. A smaller, cheaper model is usually sufficient for summaries and titles. Saved memory can be included on all configured chat routes, including ChatGPT subscription. Summary Off does not disable future title processing. See [memory](memory.md) for one complete summary with Edit/Save/Cancel, automatic single-request learning/correction/consolidation plus optional extra paid Densify → complete review → strictly shorter-only use/discard, separate authored preferences, Clear/Off, deliberate whole-history regeneration and automatic next-turn adoption. History edits invalidate the whole generated text, not unrelated preferences. Regeneration replaces direct summary edits, not preferences; ordinary in-flight snapshots remain stable. Native memory settings stay restart-only. Natural-language memory privacy is interpreted by that memory model in its normal single update request; validated current-input exclusions become durable native restrictions without erasing unrelated prior. Otherwise eligible privacy prose reaches the provider; hard restrictions remain pre-transmission. Titles retain their independent unchanged legacy pre-call guard.

Ordinary chat no longer retrieves/ingests semantic vectors or requires an embedding key/daemon. Legacy records, vectors, markers and inactive settings remain preserved for local review, without lazy migration or automatic historical export. Optional Ollama chat remains independent and operator-managed. Schema25 removes ordinary-correction/Profile erasure triggers while preserving stored rows; actual Profile currentness remains separate from privacy. The schema24/25 transitions require explicit approved copy rehearsal and separately gated primary activation, never automatic startup migration. Memory uses full frozen chat pins and debounced foreground activity/catch-up. Summary, title and local compaction operations have no application-imposed spending/attempt or tokenizer/capacity-qualification gates. The selected provider controls model capacity and may refuse a request; no clipping or fallback is substituted. Observed usage, known-price estimates, historical reservations and unknown costs remain distinct, not invoices.

Local debug traces are currently always enabled by tested application policy, regardless of `LLM_DEBUG_TRACES`. Traces visible in Profile & data may include private normalized Garmin/chat/tool context; keep them local and out of screenshots/support artifacts.
