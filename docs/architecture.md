# Architecture

## Boundaries

- `src/lib/db`: Drizzle schema, explicit SQLite schema versioning, migration integrity checks, profile, confirmed-memory, chat, Garmin data, and deletion repositories.
- `src/lib/diagnostics`: allowlisted source-beta doctor/preflight reporting and redaction canaries.
- `src/lib/garmin`: pinned stdio-only Garmin MCP boundary, normalization, checkpoints, and sync orchestration.
- `src/lib/ai`: provider registry, canonical evidence-based coaching instructions, grounded context selection, Profile/recent-chat/Garmin/confirmed-memory separation, guarded SQL/math orchestration, deterministic reliability fixtures, streaming chat, and profile extraction.
- `src/app`: local no-auth loopback UI, sync controls, chat, profile, and deletion routes.

The app stores normalized Garmin facts plus a local-only `garmin_raw_payload` archive of redacted Garmin connector/activity-detail payloads where available. `trainer-instructions.ts` owns the bounded base, planner, and synthesis instruction sections; `coaching-instructions-and-sources.md` records their evidence and limitations. Credential, token, auth, cookie, command, environment, and path-like fields are redacted before storage and before analysis-bundle exposure. Source-beta startup uses `npm run start:local`, which binds the production Next.js server to loopback by default; LAN/public exposure is unsupported.

## Trainer chat tool orchestration

`/api/chat` uses the configured model as a bounded planner over provider-visible trainer tool definitions. Tool definitions do not execute inside the AI SDK call: the server validates one selected tool call, executes up to four bounded Garmin/local tools, and passes only bounded server-authored prior-step evidence into a fresh follow-up planner or no-tool synthesis call. The route no longer runs chat-action regex branches for sync, status, ranking, verification, analysis, refresh, availability, or detail slices.

Ordered tool evidence is persisted in the existing grounding JSON as additive `toolSteps` while the primary `toolEvidence`/`grounding.tool` compatibility field remains available for current API/UI consumers. Garmin facts, activity identities, SQL rows, math rows, detail status, sync status, normalized slices, and schema/math/query summaries remain server-authored. For ad hoc analytics, the default path is now model-orchestrated schema → read-only SQL → optional bounded TypeScript math → synthesis. `describeGarminDatabase` exposes only a compact analytical contract for normalized Garmin tables, units, row counts, safe joins, examples, and forbidden data classes. `runReadOnlySql` accepts one SELECT/WITH statement over allowlisted analytical tables using a read-only SQLite connection, query-only mode, table/token validation, result caps, and sanitized errors; writes, PRAGMAs, comments, stacked statements, auth/session/account/verification tables, raw payload dumps, paths, secrets, connector handles, environment/process/network data, raw FIT, and unrestricted stream dumps are rejected. `runMathAnalysis` operates only on same-turn SQL result handles using bounded TypeScript formula/ranking/normalization/aggregation/summary operations; it has no database, filesystem, network, process, environment, connector, or arbitrary script access. The tool budget is one schema call, two SQL calls, one math call, and four total tool executions per turn; side-effect tools remain deduped. `runGeneratedGarminAnalysis` is retained only behind `ENABLE_GENERATED_GARMIN_ANALYSIS=true` as a deprecated internal fallback and is disabled by default, so ordinary ad hoc analytics no longer depend on arbitrary generated Python. After successful tool execution, the model may produce a final user-facing trainer answer from bounded server-authored evidence; deterministic concise limitation text remains the fail-closed fallback for rejected, failed, invalid, provider-error, empty-synthesis, or budget-exhausted paths. The ordinary transcript shows synthesized prose plus only a generic local-data marker, while detailed summaries/privacy/tool-step metadata stay in API and stored grounding rather than the visible message body.
