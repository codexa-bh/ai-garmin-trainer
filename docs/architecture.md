# Architecture

## Boundaries

- `src/lib/db`: Drizzle schema, explicit SQLite schema versioning, migration integrity checks, profile, confirmed-memory, chat, Garmin data, and deletion repositories.
- `src/lib/diagnostics`: allowlisted source-beta doctor/preflight reporting and redaction canaries.
- `src/lib/garmin`: pinned stdio-only Garmin MCP boundary, normalization, checkpoints, and sync orchestration.
- `src/lib/ai`: provider registry, grounded context selection, non-medical prompts, Profile/recent-chat/Garmin/confirmed-memory separation, deterministic reliability fixtures, streaming chat, and profile extraction.
- `src/app`: local no-auth loopback UI, sync controls, chat, profile, and deletion routes.

The app stores normalized Garmin facts plus a local-only `garmin_raw_payload` archive of redacted Garmin connector/activity-detail payloads where available. Credential, token, auth, cookie, command, environment, and path-like fields are redacted before storage and before analysis-bundle exposure. Source-beta startup uses `npm run start:local`, which binds the production Next.js server to loopback by default; LAN/public exposure is unsupported.

## Trainer chat tool orchestration

`/api/chat` uses the configured model as a bounded planner over provider-visible trainer tool definitions. Tool definitions do not execute inside the AI SDK call: the server validates one selected tool call, executes at most two sequential Garmin/local tools, and passes only bounded server-authored prior-step evidence into a fresh follow-up planner or no-tool synthesis call. The route no longer runs chat-action regex branches for sync, status, ranking, verification, analysis, refresh, availability, or detail slices.

Ordered tool evidence is persisted in the existing grounding JSON as additive `toolSteps` while the primary `toolEvidence`/`grounding.tool` compatibility field remains available for current API/UI consumers. Garmin facts, activity identities, dataset-script rows, detail status, sync status, normalized slices, and generated-analysis manifests remain server-authored. For ad hoc analytics, `runGeneratedGarminAnalysis` now requires an LLM-authored Python script over explicit named bounded datasets (`activities`, `dailyHealth`, `activityDetails`, and/or `rawPayloads`) instead of fixed app-owned criteria or hidden default ranking scripts. The runner builds a dataset manifest, validates/runs Python in an isolated local subprocess (`python3 -I -S`, no secret environment, safe builtins plus a curated standard-library import subset, AST name/dunder/loop denial, timeout, stdout/result caps), and accepts only bounded JSON results whose Garmin IDs, when present, exist in the provided dataset. Filesystem, network, process, environment, SQL, connector, credential, raw FIT, and unrestricted-stream access remain forbidden. Repairable generated-script/result failures such as runtime errors, syntax errors, non-JSON output, invalid result shape, oversized output, or timeout carry bounded server-authored reason/detail/hint evidence into one fresh corrected planner call within the existing two-tool turn budget; safety denials and provider/tool validation failures are not retried. After successful tool execution, the model may produce a final user-facing trainer answer from bounded server-authored evidence; deterministic concise limitation text remains the fail-closed fallback for rejected, failed, invalid, provider-error, empty-synthesis, retry-exhausted, or budget-exhausted paths. The ordinary transcript shows synthesized prose plus only a generic local-data marker, while detailed summaries/privacy/tool-step metadata stay in API and stored grounding rather than the visible message body.
