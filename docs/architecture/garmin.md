# Architecture: Garmin application and adapters

Part of the [architecture overview](../architecture.md).

## Garmin application and adapter boundary

Sync follows `api/sync → garmin/composition → sync-import`; targeted detail follows
`api/activity-detail → composition → detail-requests → detail-import`. The CLI and
local-data tool call the same composed imports directly; there is no separate
`importer.ts` compatibility facade or old forward-sync implementation.
`createGarminImports` binds explicit named
reader operations, synchronous import storage, request-time config and a clock.
`baseline-import.ts` owns athlete/body refresh failure and preservation policy;
`detail-import.ts` owns effort/detail attempts, partial success and lifecycle;
`import-policy.ts` owns date formatting and detail error classification; pure `history-policy.ts` owns additive versioned family progress, unknown-boundary semantics, UTC date arithmetic and the finite Sync admission contract. Pure `scope-policy.ts` classifies saved versus configured exploration scope (same, reconcilable finite-limit → automatic, or a closed blocked recovery) and plans that one explicit transition; `sync-policy.ts::historicalIntentAdmitted` is the single latest/history/discover admission used by HTTP, the application and the hook. The import store's `saveCheckpoints` commits each operation/history/discovery (or latest) snapshot in one transaction. Contracts live in
`import-contracts.ts`, `import-ports.ts` and existing feature types, not DB types.

`failure.ts` is a pure closed failure base: adapters raise subclasses whose message is fixed vocabulary (the official reader's `OfficialApiError`, the missing-key message), so the application surfaces them unchanged and keeps every other error generic. `garmin_history_v1` may temporarily hold version 2 only while an expanded activity window keeps its frozen lower bound (`activities.windowStart`); prior builds refuse that state rather than re-page a widened window, and it returns to version 1 when the window completes. Additive `expandedFrom` records the earlier limit. Under automatic scope, additive discovery `noDataBefore`/`oldestPositive` record where a full year without wellness data stopped exploration; health/activity/body cursors treat `noDataBefore` like a limit.

`official-reader.ts` owns wire parsing, activity/health/detail normalization,
in-process FIT and archive dispatch. Profile/body/FIT-baseline values remain
unknown inputs to the existing pure, validating feature normalizers; no vendor
SDK or arbitrary endpoint dispatcher enters application ports. Composition
supplies the user's key capability and transport from `connection.ts` and the
repository archive writer, which still redacts before persistence. The archive
precedes normalization and normalized writes. Authentication/rate-limit failures
stop before further reads. Unknown/malformed responses never become successful
empty coverage.
No raw archive is exposed to the application store or HTTP response.

Composition performs no DB/env/clock/client work at import time. Sync records its
run before reader construction, starts/closes one reader per invocation and keeps
initial DTO reads outside its try/finally. Standalone effort converts startup
errors to failed results, while standalone detail propagates startup errors.
Close remains synchronous and is not swallowed. The new `garmin_history_v1` checkpoint keeps separate reverse health, frozen activity-window/page and body-history positions; old global cursors are never reused as range identities. Idempotent normalized writes precede cursor saves, so a crash replays rather than skips. Existing evidenced historical dates can be traversed without remote re-fetch; no local minimum becomes a remote lower-bound proof. Failed health dates remain separately unresolved. Body writes merge date-keyed history and preserve current facts during older-only batches. No schema migration/reset is needed.

The bounded tool/maintenance invocation retains 96 HTTP requests/180 seconds and 30 seconds per request. Explicit interactive POST selects one foreground operation with a non-resetting 30-minute/480-request ceiling; history/discovery retain at least 1,000ms between serial dispatches, while explicit latest removes artificial spacing. The supplied wait/clock/admission ports count startup, nested calls and pacing without introducing ambient capabilities into policy. One application claim spans all batches, normalized/cursor/operation settlement and owned close. Recent facts and common profile/FIT supplements run once; historical families rotate to avoid starvation under slow reads. Safe pre-dispatch batch exhaustion may continue; an in-flight timeout, connection/protocol/auth/rate/storage failure or no progress stops dispatch without retries. The outer reader owns timers/cancellation and reports even failures swallowed by best-effort baseline/detail policy back to interactive admission.

Pending detail enumeration has no default ceiling (explicit maintenance selections retain their limits). The foreground application drains terminal-removing selections without offsets, rechecks after historical activity pages and at settlement, and stops on a failed result or no progress. Pre-dispatch interactive batch renewal preserves the reader/claim, pacing and cumulative counters; ambiguous in-flight failures never renew/retry. Additive `garmin_sync_v1` stores intent/outcome/typed stop reason, attempted/completed/failed detail counts and known remaining work alongside existing latest/family checkpoints. Result and passive summary share that operation; live summary additionally recomputes current unique eligibility. Legacy absence is unknown; unsupported/corrupt operation versions preserve bytes and refuse mutation. Prior compatible source can ignore the new key while preserving DB/backups. SQLite schema and normalized detail shapes are unchanged; same-task populated-copy eligibility/re-sync, preservation and idempotency remain required.

Pure `sync-policy.ts` owns the closed latest/history intent and authoritative historical action/next-work projection. The existing import application supplies current scope, validated checkpoints and the same SQL repair selection used for execution; `/api/summary` composes that passive projection alongside stored counts. Results and reload use the same policy, never text parsing or history-existence JSX rules. Latest writes only additive `garmin_latest_v1` settlement/counters and leaves family/discovery checkpoints byte-identical, including unfinished history. Explicit history refuses active, changed-scope, unsupported or failed/no-progress recovery state; its signature excludes repair rotation alone as useful progress. Existing legacy callers retain their bounded behavior. The persistent hook invalidates stale/superseded summary admission, sends explicit intent, retains disclosure/log state and requires refreshed settlement after transport loss. Technical logs are collapsed and not a hidden live region; upsert counters are processed/refreshed, never inferred new imports.

Pure `latest-policy.ts` owns desktop-local latest health day-end/finality and the additive validated `garmin_latest_freshness_v1` checkpoint. Stored-date enumeration is uncapped. Pure `coverage-policy.ts` judges whether the official daily summary covered a whole local day (midnight-to-midnight local chronology with consistent GMT offsets, DST-aware); the day becomes final with `source: "coverage"` only once it has ended and its normalized write succeeded. It never records an upload or claims watch-upload verification. The first official run over earlier connector state applies `transitionToCoverage`: the recent 14 local dates lose upload-based finality and are rechecked, older upload-based finals stay `legacy`, non-final days stay non-final; the result is persisted before reading, so interruption replays. Normalized data commits before finality metadata. Finality is orthogonal to availability. History/discovery bytes and UTC activity/history ranges remain unchanged. Daily profile/zone attempt days commit before dispatch, include body callers and persist failures; FIT uses a successful applicable newest-activity ID and merges usable facts without re-reading profile or overwriting attempt metadata. No schema migration, background work or new public endpoint is added.

Pure `discovery-policy.ts` owns the discovery checkpoint and step-hint contract; the official reader derives the hint from a year of daily summaries (`officialDiscoveryHint`), never reading below a selected limit. A full range with no wellness data is an observed empty year; a null or truncated range is unknown. No negative or cross-family coverage/bound is inferred, and raw payloads are not retained as discovery provenance. `garmin_discovery_v1` is additive alongside unchanged family v1: hint range/count/source/time, positive date queue/cursor and latest operation phase/attempts/batches/outcome/stop reason. Valid v1 checkpoints resume without resets; unknown new state refuses. Normalized writes precede family/queue cursor saves for replay. A compatible prior revision ignores the new key and preserves normalized data/backups; returning forward revalidates it. HTTP owns NDJSON/disconnect; persistent shell Sync survives navigation. Setup/launch/summary never start work; a lost response reconciles durable/live truth and restart requires explicit Resume. Persisted running without a live owner is interrupted, not active. No durable scheduler, generic job API or model-driven 30-minute continuation is introduced.

`tests/garmin-application.test.ts` uses supplied fake capabilities and ordered
write/event journals, without infrastructure mocks; source-independent policy
suites drive it through a test-only legacy-shaped reader double
(`tests/legacy-reader-double.ts`). `official-reader.test.ts` and
`official-composed-sync.test.ts` check wire/archive/FIT order and coverage with an
authored HTTP transport; `garmin-production-wiring.test.ts` exercises actual
HTTP/composition/official reader/SQLite wiring with only `fetch` authored.
`garmin-dependencies.test.ts` follows type-inclusive closures and rejects outer
imports/ambient capabilities; `garmin-product-exclusion.test.ts` keeps connector,
helper, child-process and external-tool references out of product code. `garmin-history.test.ts` additionally exercises real HTTP/SQLite discovery, sparse metric islands, preserved old weight rows, fatal/protocol failures, cancellation/exclusion and nested admission/deadlines. SQL schema is unchanged, but checkpoint/body-merge semantics require same-task populated-copy transition/re-sync verification; they are not a data back-sync no-op. Source rollback ignores additive discovery keys and preserves normalized records/backups; the prior exhaustive policy is not bounded-sync certification.

### Official Personal API reader

`official-reader.ts` is the product's only `GarminReader`, over Garmin's documented Personal API. Composition constructs it per operation with the user's key capability from `connection.ts` (installed once at startup from the native private frame) and global `fetch`; an admitted isolated synthetic smoke run may route the same requests to its owned loopback fixture, which ordinary configuration cannot select. `GET /api/sync` is the only explicit connection check (one key exchange plus profile read); no startup, Settings or summary probe exists.

- `official-client.ts` is the only HTTPS owner: a fixed `https://personal.connectapi.garmin.com` origin, manual redirects, an injected `fetch` and injected API-key capability, `POST` token exchange read as bounded raw text, an in-memory bearer reacquired before its documented 24-hour lifetime, and at most one reacquisition after a cached bearer is rejected. A rejected key is never retried. Every actual request, including the exchange and downloads, asks the sync control for admission, so budget, pacing and cancellation count real requests, not cache hits. Failures use the closed vocabulary in `official-error.ts` (no URL, header, key, token or vendor body ever appears).
- `official-normalize.ts` translates wire shapes (nested daily summaries, ranges, grams, epoch milliseconds, `sleepScores.overall.value`, separate HRV) into the existing normalizer inputs. `official-reader.ts` orchestrates them, plans ≤31-date blocks from `planDailyHealth`, and keeps only operation-local caches.
- `official-zip.ts` admits the one original FIT file inside Garmin's ZIP under hard size, ratio, entry and name bounds; `official-fit.ts` decodes it once in-process (`fit-file-parser`, MIT) for detail streams, the athlete baseline and HR time in zones. Session-referenced `time_in_zone` is exact; exact activity-list buckets are the next source; sampled heart rate with the file's own boundaries is labelled `garmin_official_estimate`; otherwise the zone time is unavailable, never zero.
- Provenance: new facts use `garmin_official`; rows imported by the retired connector keep `garmin_mcp` and are never bulk-renamed. Archive labels are `official_*` and map to the same logical kinds as the retired tool names in repair queries.
