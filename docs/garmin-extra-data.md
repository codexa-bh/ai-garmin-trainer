# Additional Garmin evidence and its explicit history backfill

Explicit official Sync imports eight additional evidence groups beside the existing activity and daily-health facts. The trainer receives selected recovery facts in its bounded per-turn preview and selected activity facts in the default known-ID numerical overview; guarded SQL/math supplies historical windows, comparisons, full detail and omitted groups. No new dashboard UI is added. This page is the field/coverage contract and the maintenance runbook for filling existing history. Schema 29 adds these relations; older builds refuse a schema-29 database.

## Field and coverage contract

| Group                       | Relation (join)                                                                                           | Meaning and units                                                                                                                                                                                                                                                                                                                                                                       |
| --------------------------- | --------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Sleep sub-scores and timing | `daily_sleep_detail`, `daily_sleep_score_component` (date → `daily_health.date`)                          | Garmin's sleep date. GMT epoch ms plus source-local wall clock and the offset from the source's own timestamps, never the host timezone. Components `overall/deep/light/rem` carry a 0–100 value. `total_duration/stress/awake_count/restlessness` carry a qualifier and optimal range only, with no invented score. Feedback and insights are Garmin enum codes; free text is dropped. |
| HRV baseline                | `daily_hrv_detail` (date)                                                                                 | Weekly average, best 5-minute night value and Garmin's personal baseline bounds in ms (nightly value/status stay in `daily_health`). These are Garmin evidence, not app thresholds.                                                                                                                                                                                                     |
| VO2 max                     | `vo2_max_reading` (date + branch `generic/cycling/rowing`)                                                | Sparse dated measurements in ml/kg/min, rounded and precise, with source sport when supplied. Never a daily series and never forward-filled.                                                                                                                                                                                                                                            |
| Body Battery                | `daily_body_battery`, `body_battery_event` (date); `activity_extra_metrics.body_battery_delta` (activity) | Daily min/max/charged/drained/latest and the source's end-of-day value (latest is not end of day). Events carry a signed impact, keyed by type + GMT start + duration. Events are linked to an activity only when Garmin names one, never by time. The activity delta is signed, not a level. Range data only: no single-day wake/sleep reads.                                          |
| Stress breakdown            | `daily_stress` (date)                                                                                     | Bucket durations in seconds (source milliseconds converted). Fractions are 0–1 only when the row's proportions agree with its own durations; otherwise they are null. Activity and uncategorized time are not high stress.                                                                                                                                                              |
| Per-lap HR zones            | `activity_lap_hr_zone_time` (activity + lap number + bucket)                                              | From the activity file's lap-referenced `time_in_zone`, joined by the lap's own FIT `message_index`. Bucket 0 is below zone 1, 1–5 are zones, 6+ are above, each with that file's own boundaries/method/max/resting HR. Missing or duplicate references make the activity's lap zones unavailable. Session totals in `activity_hr_zone_time` are unchanged; never add the two.          |
| Running dynamics            | `activity_extra_metrics` (activity); `activity_lap.fit_*`                                                 | List cadence is steps/min and stride is centimetres. FIT cadence is **cycles/min** including the fraction (a stride for foot sports, a revolution for cycling) plus total cycles. FIT oscillation/step length are converted from mm. Ground-contact/oscillation/ratio/balance/grade-adjusted speed exist only when a sensor recorded them.                                              |
| Snowboard splits            | `activity_split_summary` (activity + split type)                                                          | Per-type **totals** for `SKI_RUN_SPLIT/SKI_LIFT_SPLIT/ASCENT_SPLIT/DESCENT_SPLIT/TRANSITION` from the activity list: count, total duration/distance, best single split. They are not individual runs.                                                                                                                                                                                   |

`garmin_data_coverage(data_group, subject_type, subject_id, status, reason)` records, per group and date/activity, `populated`, `empty` (the source replied without it), `unavailable` (the source cannot supply it, for example no original file or stored laps that differ from the file) or `failed` (the read failed). **No row means not yet imported or backfilled**, which is unknown, not empty or zero. A later failed or empty read never demotes `populated`.

Foreground Sync derives these groups from the replies it already reads. Daily groups come from the same 31-day ranges, plus one VO2 range read per planned block. List extras come from the same activity pages, and lap evidence from the single FIT decode per activity. Scalars merge with coalesce, so a missing value never erases a stored one. Sleep components merge per component. Event and split sets are replaced only when the source list was returned. A detail refresh replaces lap zones with its lap set. KPI recipe freshness includes these relations. Deleting Garmin data deletes them too.

## Default trainer evidence

The recovery preview reads the ten newest **existing `daily_health` dates**, in descending order. It adds Garmin sleep score (0–100) and overall qualifier, weekly HRV with Garmin balanced baseline bounds (ms, distinct from nightly HRV/status), daily Body Battery charged/drained points (not levels or activity delta), and `high_seconds / 60` as high-stress minutes (one decimal; no activity/uncategorized time). Each selected group has independent coverage. Legacy facts remain visible even without extra-group coverage; null within a populated group is still missing. Extra-only dates never enter the preview, values are never carried forward and child components/events cannot multiply dates. Normalized enum codes are at most 64 ASCII characters; free text is excluded.

`getActivityDashboard` for an already known imported ID reads signed activity battery delta, list cadence/stride, FIT session/lap cadence and step length, stored lap-zone buckets and all five snowboard per-type summaries. Units retain their sources: list cadence steps/min and stride cm; FIT cadence fractional cycles/min, total cycles and step length m. No automatic doubling or fictitious optional sensor values. Lap zones retain stored lap-number association and historical file boundaries/method/max/resting HR; buckets 0 and 6+ are below/above, not zone 1–5 totals. Never add lap to session zone totals. Snow rows remain per-type aggregates, never individual runs/lifts; duration/distance/speed/elevation and best-split facts keep seconds/metres/metres-per-second.

Measurements, units, group coverage and limits precede optional detail. Supplementary lap evidence has exact stored lap counts and returns at most 20 laps × 8 buckets, with per-lap returned/omitted counts; all 5 closed split types fit with type counts. Existing optional overview laps/terrain stay capped at 20; the legacy dashboard source cap of 100 still cannot establish its exact total. The selected ten-day recovery text is tested below 8,000 characters and supplementary activity JSON below 90,000 characters, without raising generic tool limits. Native/legacy provider evidence preserves the complete finite overview. No raw FIT, GPS, paths, charts/streams, implicit fetch/import or focused-UI selection enters numerical evidence; existing explicitly selected image handling remains separate.

The preview guides discovery, not complete history or required current-turn verification. Historical/event-relative recovery needs guarded tools; same-day all-day totals are not proven pre-start state. Missing coverage is `not_imported_or_backfilled`, distinct from `empty`, `unavailable`, `failed` and true zero. SQL/math remain the route for comparisons and detail beyond these bounds. These are read-only schema-29 consumers: no migration/backfill/back-sync is needed for this projection change, and source revert on a compatible schema-29 build is sufficient rollback. Existing missing history still needs the explicitly authorized backfill below.

## Explicit history backfill

Existing history needs **fresh official reads**: earlier archives do not contain these fields. `npm run backfill:garmin-extra` is an explicit maintenance command, never run by startup, Sync or Settings. It shares the official reader and normalizers but writes only these relations, coverage and its own `garmin_extra_backfill` checkpoint. It never changes existing activity/daily-health/lap facts, sync/history/finality checkpoints or other domains. It never creates days or activities: daily groups are read only for stored `daily_health` dates and list/lap evidence only for stored activities. Lap evidence is written only when the stored laps match the file's laps (count, number, start instant within 2 s); otherwise the activity's lap zones are `unavailable`.

### Preconditions (every invocation needs current authority)

1. Exact approved target, stopped app and every other writer stopped; the shared writer lease must be acquirable. Never kill processes or delete a lease to force admission.
2. A verified, WAL-consistent recovery backup made before any write (`npm run db:migrate` makes one for an upgrade; otherwise use an SQLite online backup and verify integrity, FKs and schema).
3. Explicit migration to schema 29 and integrity verification: `DATABASE_PATH='/exact/approved.sqlite' npm run db:migrate`. The backfill refuses any other schema.
4. A rehearsal of the same command on a disposable copy of the same target.

### Run

```bash
# Key on stdin only: never argv, environment, logs or chat.
DATABASE_PATH='/exact/approved.sqlite' npm run -s backfill:garmin-extra -- \
  --from 2024-07-01 --to 2026-11-19 [--max-requests 150] [--max-seconds 600] < private-key-input
```

Requests are serial, at least 1 s apart, and capped per invocation (defaults 150 requests/600 s; maxima 1000/3600). Phases run in order: daily ranges in 31-day blocks (summaries, sleep, HRV, Body Battery and VO2), activity pages in 90-day windows padded one day each side, then one FIT download per activity. Already-settled subjects (any non-`failed` coverage) are skipped, so repeats cost no reads and retry only failures.

Each batch's data and checkpoint commit in one transaction. A crash leaves neither, and the next invocation replays that batch idempotently. The checkpoint binds the contract, schema, target (hash of the canonical path) and date bounds. A mismatched or corrupt checkpoint refuses without being rewritten. Cancellation (SIGINT/SIGTERM), the request/time budget, authentication failure and HTTP 429 **stop** with durable progress. Isolated service/protocol failures mark only that batch's groups `failed`. Three consecutive failures stop the run.

**Account guard.** The Personal API exposes no stable account identity to the reader, so the backfill checks evidence before writing. Stored activities in each window must recognisably reappear in the fresh list, and stored daily steps must match where both exist. Otherwise it refuses with `account-or-target-mismatch` and writes nothing for that batch.

Output is one JSON line containing `status` (`completed|stopped|refused`), a closed reason, pass/phase, counts (dates/windows/details read or failed, `lapsMismatched`, `localNotInSource`, `sourceNotLocal`), requests by endpoint family, per-group coverage counts, integrity and FK results. It never contains the key, IDs, measurements, payloads or paths.

### Recovery

A stopped or refused run leaves the target consistent. Inspect the result and coverage, then continue only under current authority with the same bounds; never reset or edit the checkpoint to force rereads. A source revert is not a schema rollback: keep the recovery backup and newer writes and use a compatible forward fix or a separately reconciled restore. Reopen only a schema-29-compatible app.
